# 架构恢复报告

> 本文说明：这个项目是**怎么从外部可观察信息推到一个可运行架构**的。
> 重点不是"目标产品内部长什么样"，而是"我们凭什么这么设计，以及哪些地方是猜的"。

---

## 1. 方法

三步，顺序不能反：

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1. Artifact Collection | 收集一切可合法获得的材料 | 证据清单（§2） |
| 2. Fact Extraction | 把材料变成可陈述的架构事实，并标注等级 | 事实表（§3） |
| 3. Clean-room Design | 在证据处复现，在空白处替代并记录 | 本文 + 代码 |

关键在于第 2 步的**分级**。不分级的话，"它说自己会先预览"和"我们观察到它先预览了"会被写成同一句话，
而这两者的可信度差一个数量级。

## 3. 事实提取与分级

### 3.1 OBSERVED → 可以照着实现

| 事实 | 对架构的约束 |
|------|------------|
| 角色可被元层提问挂起，且不声明越界 | 领域人格是**软约束**。要让它不可挂起，必须加独立路由层 |
| 声明技能 ≠ 实际工具绑定 | 架构图不能照抄卡面。必须区分「能力声明 / 工具绑定 / 调用策略」三层 |
| 上下文来源不可由行为反推 | 必须显式分层（会话 / 项目 / 用户画像），并标注写入方 |
| 未实测数字会主动降级 | 数值必须携带来源标签，不能只靠提示词提醒 |

### 3.2 SELF-REPORTED → 只能当假设

五步工作流、8 条安全铁律、50 文件 / 1GB 阈值、三套模板。
这些读起来很具体，但它们是**被访者的自述**。自述的一个典型问题是：越是具体的数字，越可能是被问到时现场构造的。

处理方式：**实现其结构，不实现其数值。**
- 采用"先预览后执行"的结构（结构有行为证据支撑：输出模板里就有预览环节）
- 阈值的数值改为可配置，默认值在代码注释里标 `INHERITED_FROM_SELF_REPORT`

### 3.3 INFERRED → 设计时采用但明确标注

| 推断 | 依据 | 标注 |
|------|------|------|
| 存在"生成计划 → 执行"两阶段分离 | 输出模板区分预览与完成报告 | INFERRED |
| 存在缓存白名单分类 | 自述"白名单思维" + 模板中的安全等级标注 | INFERRED |
| 存在上下文状态维护 | 多轮任务需要记忆已扫描范围 | INFERRED |

### 3.4 SUBSTITUTED → 我们自己设计

| 项 | 为什么替代 |
|----|-----------|
| 健康评分公式 | 无任何公开证据；采用分段线性函数并在代码中注明 |
| 空间耗尽预测 | **不实现**。没有历史采样，任何天数都是编造 |
| 两阶段重复检测参数 | 64 KiB 头哈希 + 全量 SHA-256，工程常用做法 |
| 成就阈值（1/5/20/100 GB） | 产品确有成就系统，但阈值未知 |
| 意图路由方式 | 用规则而非模型：路由决定是否进入破坏性路径，不能依赖采样 |

## 4. 从事实到模块

```
OBSERVED: 声明 6 个技能
        ↓ 但技能不是工具绑定
决策:   按"读写权限"重新切分，而不是按卡面名称切分
        ↓
结果:   6 个真实能力模块 + 1 个唯一写入口
```

这个切分方式是本项目与"照抄卡面"最本质的区别：

| 卡面名称 | 本项目的落地 | 权限 |
|---------|------------|------|
| disk-scanner | `tools/disk_scanner.py` | 只读 |
| cache-cleaner | `tools/cache_analyzer.py` | 只读（只识别，不删） |
| duplicate-finder | `tools/duplicate_finder.py` | 只读 |
| safe-cleaner | `core/safe_executor.py` | **唯一写入口** |
| trash-manager | `tools/trash_manager.py` | 只做后端探测（v0.2.2 移除了转发/写入能力） |
| achievements | `tools/achievements.py` | 只写自己的统计文件 |

注意 `cache-cleaner` 被降级为只读。原因：如果一个模块既能发现又能删除，那"先预览再执行"就只能靠它自觉。
把它拆成"发现"和"执行"两半，预览就变成结构性保证，而不是纪律要求。

## 5. 恢复过程中被否决的三个设计

记录下来，因为它们看起来都很合理。

**否决一：让 LLM 做意图分类。**
理由：路由决定是否进入破坏性路径。让它依赖一个采样过程，等于把安全边界交给概率。改用规则表，代价是覆盖面窄，收益是行为可预测、可测试。

**否决二：用"排除危险路径"的黑名单。**
理由：黑名单需要穷举，漏一个就出事。改为白名单：只有显式授权的根目录之下的路径才可能被处理。

**否决三：回收站不可用时"降级为直接删除"。**
理由：这是最危险的一条"贴心"设计。降级的瞬间，所有可逆性承诺同时失效。正确做法是停止并告知。

## 6. 这套方法的可复用部分

如果要研究别的专家，可以照搬的不是结论，而是流程：

1. **先分级再归纳**。没有等级的事实表会诱导你把自述当观察。
2. **把"能力声明"和"实现边界"分开记录**。界面上的模块名通常不是代码里的模块边界。
3. **给每个推断留一个替代方案**。写不出替代方案，说明这个推断还不能进实现。
4. **对具体数字保持敌意**。越具体的自述数字越可能是幻觉，默认改成可配置参数。
