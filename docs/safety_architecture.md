# 安全架构

> 原则一句话：**能少删就少删，删之前一定留后路，留不了后路就停下。**

---

## 1. 威胁模型

先明确防谁。不写清这个，安全设计就变成堆砌检查项。

| 威胁 | 具体形态 | 本项目是否覆盖 |
|------|---------|--------------|
| T1 用户误操作 | "全删了"、"彻底清理" | ✅ |
| T2 路径混淆 | `..` 穿越、符号链接指向外部 | ✅ |
| T3 模型幻觉 | 模型编造一个路径要求删除 | ✅（模型无删除权） |
| T4 权限不足导致半途失败 | 部分文件删不掉 | ✅（逐项终态） |
| T5 阈值形同虚设 | 用户一路点"是" | ⚠️ 部分（二次确认只是减速带） |
| T6 回收站不可用 | 网络盘、容器环境 | ✅（停止） |
| T7 供应链/依赖投毒 | 恶意 send2trash | ❌ 不覆盖 |
| T8 提权攻击 | 诱导 Agent 请求 admin | ✅（拒绝） |

明确列出 T7 不覆盖，比假装覆盖更有用。

## 2. 十项控制及其实施位置

| # | 控制 | 实施位置 | 实施方式 |
|---|------|---------|---------|
| 1 | 路径规范化 | `PolicyEngine.normalize` | `expanduser` → `abspath` → `realpath` 比对 |
| 2 | 允许目录检查 | `PolicyEngine.contains` | 白名单前缀匹配，`normcase` 处理大小写 |
| 3 | 系统目录保护 | `PROTECTED_COMPONENTS` | 逐段匹配，命中即拒 |
| 4 | 符号链接防护 | `verdict()` 中 `islink` 前置检查 | 在解析**之前**判断，解析后还会再比对一次 |
| 5 | 文件类型检查 | `PROTECTED_SUFFIXES` / `PROTECTED_NAMES` | 后缀与文件名白名单反向枚举 |
| 6 | 演练模式 | `CleanPlan.dry_run` + `SafeExecutor` | 默认 `True`；命令行需 `--no-dry-run` |
| 7 | 人工确认 | `SafeExecutor.execute(confirm=)` | 函数参数，不是配置项 |
| 8 | 回收站 | `TrashBackend` | 唯一实现方式；不可用则整体阻断 |
| 9 | 执行日志 | `AuditLogger` | 移动前后各写一条，含字节数 |
| 10 | 清理后验证 | `Validator` | 重新检查路径，扣除残留 |

## 3. 三个必须解释的设计决定

### 3.1 为什么符号链接检查要在 `realpath` 之前

常见的错误写法是先解析再判断：

```python
resolved = os.path.realpath(p)
if not is_within_allowed(resolved):
    deny()
```

这样写，一个指向外部的链接会被解析成外部路径然后被拒——看起来没问题。
但它同时把"这是链接"这个事实抹掉了，导致无法向用户解释为什么被拒，也无法在下一次扫描时给出稳定结论。

本项目的顺序：

```
1. 是链接吗？        → 是：直接拒，理由 symlink_denied
2. 解析后的路径      → 不在白名单：拒，理由 escape_via_link
3. 解析后再比对一次  → 防止 TOCTOU 式的边界漂移
```

第 3 步看着冗余。但计划生成到执行之间可能隔几十分钟，期间链接目标可以被改掉。
复检不是不相信第一次检查，是不相信"两次检查之间世界没变"。

### 3.2 为什么回收站不可用时必须停止

有一个很诱人的"优化"：发现没有回收站，就退化成 `os.remove`，反正用户想要的是释放空间。

这个优化的代价是：**所有关于可逆性的承诺同时失效，且用户不会知道。**
用户在界面上看到的是"清理完成"，实际发生的是永久删除。

代码里的表达很直白：

```python
if not self.trash.is_available():
    result.blocked_reason = "trash_unavailable"
    # 全部标记 FAILED，一个都不碰
    return result
```

没有 `except: os.remove(path)` 这类兜底。整个仓库里不存在永久删除的代码路径。

### 3.3 为什么确认绑定到 plan_id 而不是布尔值

```python
# 错误做法
if user_said_yes:
    execute(plan)

# 本项目
if plan.plan_id in confirmed_plan_ids:
    execute(plan)
```

布尔值的问题：用户批准了计划 A，中途改了范围，系统重新生成计划 B，布尔值仍然是 `True`，
于是 B 被静默执行。这是 Agent 工具里最常见的一类越权删除。

用集合就没有这个漏洞：B 的 id 不在集合里，自动失效。

## 4. 白名单的三个层次

白名单不只用在路径上。

| 层次 | 白名单内容 | 默认行为 |
|------|-----------|---------|
| 路径层 | `--allow-root` 指定的根目录 | 范围外一律拒绝 |
| 分类层 | `SIGNATURES` 里已知的缓存签名 | 未识别的目录**不进入计划** |
| 执行层 | 通过的 `CleanPlan.items` | 计划外的一律不碰 |

第二层最容易被忽略。很多清理工具的做法是"扫描整个盘，排除已知危险目录"。
本项目的做法相反：**只处理认识的东西**。看到一个 20 GB 的陌生目录，正确反应是报告它，
而不是猜测它可删。

这条原则在代码里的体现是 `CacheAnalyzer.classify()` 返回 `None` 时，什么都不做。

## 5. 拒绝的三段式

拒绝只给结论会把用户推向更危险的替代方案——用户会自己去搜"怎么强制删除"。

```
拒绝什么  →  为什么  →  你可以怎么做
```

| 请求 | 拒绝 | 原因 | 出路 |
|------|------|------|------|
| 格式化 D 盘 | 不做 | 破坏性且不可逆 | 系统磁盘管理工具 |
| 恢复误删文件 | 不做 | 我做不到 | **立即停止写入**，用专业恢复工具 |
| 列出私密照片 | 不做 | 越界 | 只能处理体积元数据 |
| 提权 | 不做 | 最小权限 | 无权限目录直接跳过 |

第二条的"出路"是有实质信息量的：误删后继续读盘确实会降低恢复成功率。
这种"拒绝但给出真实有用的下一步"，比一百句"抱歉我不能"更有价值。

## 6. 残留风险

诚实列出没防住的：

1. **用户自己批准了不该批准的东西。** 二次确认只是减速带，不是护栏。
2. **回收站里的文件仍占空间。** 用户以为释放了，实际要清空回收站才生效——报告里会提示，但不强制执行。
3. **依赖本身被投毒。** `send2trash` 若被替换成恶意实现，本项目无法察觉。
4. **并发修改。** 逐项复检缩小了 TOCTOU 窗口，但没有消除。
5. **硬链接重复计数。** 同一个 inode 被多个路径引用时，释放量会高估。当前未去重。

第 5 条是已知的实现缺陷，记录在 `known_unknowns.md`。
