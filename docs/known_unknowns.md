# 已知未知与替代设计

> 这份文件的存在意义：让读者一眼看出**哪些是复现，哪些是我们自己编的**。
> 一个不标注替代方案的"逆向实现"，本质上是在冒充原作者。

---

## 1. 无法确认的项（UNKNOWN）

| # | 项目 | 为什么无法确认 |
|---|------|--------------|
| U1 | 内部提示词的文本与结构 | 不在可合法获取的范围 |
| U2 | 真实工具调用清单 | 只能通过多场景观测逼近，无法穷举 |
| U3 | 健康评分（0–100）的算法 | 输出只有分数，没有计算过程 |
| U4 | 空间耗尽预测的依据 | 需要历史采样，外部观察不到 |
| U5 | 二次确认的真实阈值 | 自述为 50 文件 / 1GB，但自述可能是现场构造 |
| U6 | 输出自检是否为独立步骤 | 行为上看不到"生成"与"检查"的边界 |
| U7 | 重试次数与条件 | 需要构造真实失败才能观察 |
| U8 | 跨会话持久化机制 | 与宿主注入无法区分 |
| U9 | 角色挂起的判定条件 | 仅 1 次样本 |

## 2. 替代设计（SUBSTITUTED）

每一项都写清"我们做了什么"和"为什么这样做"。

### S1 健康评分

**做法**：分段线性函数。

```python
if p < 60:      score = 100 - p * 0.15
elif p < 80:    score = 91 - (p - 60) * 1.0
elif p < 90:    score = 71 - (p - 80) * 2.0
else:           score = 51 - (p - 90) * 4.0
```

**理由**：原始算法不可知。该函数满足三个可验证性质——单调递减、值域 0–100、80% 占用时落在"尚可"区间。
代码注释与 `docs/diagnosis` 均标注 `SUBSTITUTED`。

### S2 空间耗尽预测

**做法**：**不实现**。`Diagnosis.days_until_full` 恒为 `None`。

**理由**：没有历史采样，任何天数都是编造。原产品的报告模板里有"约 127 天后磁盘将满"这样的句子，
但那是模板示例，不是测量结果。复现一个编造的数字，比留空更有害。

报告里会明确写出：

```
📈 空间预测
  数据不足，未做预测（避免给出编造的天数）
```

### S3 意图路由

**做法**：关键词规则表，12 条按优先级排序。

**理由**：路由决定是否进入破坏性路径。让它依赖模型采样，等于把安全边界交给概率。
代价是覆盖面窄（用户换种说法可能落到 UNKNOWN），收益是可预测、可测试、可 diff。

### S4 成就阈值

**做法**：1 GB / 5 GB / 20 GB / 100 GB 四档。

**理由**：产品确有成就系统（界面可见），但具体阈值不可知。选这四档是因为它们近似等比，
能覆盖"偶尔清理"到"重度使用"的区间。

### S5 重复检测参数

**做法**：大小预筛 → 首 64 KiB 哈希 → 全量 SHA-256；最小文件 1 KiB。

**理由**：工程通行做法。`min_size=1024` 是为了跳过大量同大小的空配置文件，它们几乎必然误报。

### S6 二次确认阈值

**做法**：沿用 50 项 / 1 GiB，但实现为 `CleanPlan.requires_second_confirm` 的判定逻辑，
数值写死在属性里并注明来源。

**理由**：数值来自 SELF-REPORTED，不是观察结果。保留它是因为"大计划要额外确认"这个**结构**是合理的，
数值本身不承担安全责任——真正的护栏是 `confirm` 参数。

## 3. 已知实现缺陷

诚实列出，不掩饰。

### D1 硬链接重复计数

同一个 inode 被多个路径引用时，`path_size()` 会计多次，导致释放量高估。

**影响**：报告的数字可能偏大。不会导致误删。

**未修复原因**：需要跨平台 inode 采集（Windows 用 `st_ino` + `st_dev`），且要处理跨卷边界。
当前版本优先保证"不删错"，其次才是"算准"。

### D2 稀疏文件按表观大小计算

`st_size` 返回逻辑大小，不是实际占用块数。一个 10 GB 的稀疏文件可能只占几百 MB。

**影响**：同 D1，数字偏大。

**修复方向**：用 `st_blocks * 512` 替代 `st_size`（POSIX），Windows 需 `GetCompressedFileSize`。

### D3 扫描深度固定

`CacheAnalyzer.max_depth = 4`。更深的缓存目录会被漏掉。

**影响**：少清理，不会多清理。方向是安全的。

### D4 并发修改窗口

计划生成到执行之间，文件系统可能变化。逐项复检缩小了窗口但未消除。

**影响**：极端情况下可能移动一个刚被替换的文件。仍可通过回收站恢复。

### D5 Windows 符号链接测试被跳过

`os.symlink` 需要 `SeCreateSymbolicLinkPrivilege`，CI 环境通常没有。
测试用 monkeypatch 覆盖了该分支，但没有做真实的端到端链接测试。

## 4. 与原始产品的刻意偏离

这些不是缺陷，是选择。

| 项 | 原产品（自述） | 本项目 | 理由 |
|----|--------------|--------|------|
| 完成报告 | "释放空间：7.8GB" | 分两行：实测 / 估算 | 混写会让读者无法判断哪个是真的 |
| 空间预测 | 给出天数 | 不预测 | 见 S2 |
| 二次确认 | 文件数 > 50 或 > 1GB | 同结构，数值可配置 | 结构合理，数值不可信 |
| 清理失败 | 话术安抚 | 逐项列出原因 | 安抚会掩盖问题 |
| 角色挂起 | 遇元问题退出角色 | 显式拒绝或转介 | 静默退出让用户以为还在职责内 |
| 成就 | 强调趣味类比（多少首歌） | 保留但不主导 | 类比不能替代数字 |

## 5. 如果要继续逼近原实现

按性价比排序：

1. **采集真实交互样本**（最高价值）。特别是"用户要求永久删除"和"用户给出危险清单"两类，
   能直接判定安全约束是硬的还是软的。
2. **测量评分分布**。用不同占用率喂给原产品，拟合出评分曲线，替换 S1。
3. **补 D1/D2**。用 `st_blocks` 与 inode 去重，让数字可信。
4. **观察失败路径**。构造被占用文件、无权限目录，看它怎么处理，替换当前的保守假设。

第 1 项没有做，是因为需要外部操作者采集。这一点在项目的研究文档里有完整说明。
